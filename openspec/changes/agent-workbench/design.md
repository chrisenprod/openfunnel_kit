# Design

## Context
Ver propuesta. El servidor central protege CRUD por cookie/Origin; resources.js concentra validación y transacciones. integration-store calcula configHash incluyendo el agente y prompts; el worker ya revalida generación y envío. La UI usa formularios compartidos.

## Goals / Non-Goals
**Goals:** documentos utilizables y recuperables, pruebas conversacionales, documentación pública y configuración técnica exclusiva de servidor. Una sola API/SQLite.
**Non-Goals:** OCR, RAG, embeddings, herramientas de búsqueda, webhooks, OpenAPI, diagnóstico adicional, procesamiento sin canal productivo, pruebas persistidas y replay de conversaciones operativas.

## Decisions
- Migración 005 añade ai_agents.business_context (texto opcional), prompts.version (entero), prompt_versions (snapshot/autor/fecha, FK cascade al borrar un prompt no referenciado), api_keys (hash SHA256 de 32 bytes aleatorios, prefijo público, scopes, vencimiento/revocación/último uso). Versiones existentes se inicializan como migration. Sin ORM/dependencias.
- GET/POST /api/api-keys y POST /api/api-keys/:id/revoke son solo sesión. Hasta 100 claves por instancia; no borrado, rotación manual creando y revocando. Expiración en días obligatoria 1–365, UI por defecto 90. Scopes con lista cerrada, límite en memoria por instancia que reinicia con el proceso.
- Bearer se autentica antes de omitir Origin, nunca mezcla cookie y Bearer. Denegación por defecto: resources:read permite GET a recursos conocidos y versiones; prompts:write permite PATCH /api/prompts/:id y POST /api/prompts/:id/restore; agents:test permite POST /api/ai_agents/:id/test. Ningún otro acceso a integraciones, auth o gestión de claves. Salud y webhook mantienen sus contratos propios.
- PATCH prompt exige expected_version entera; transacción guarda snapshot atribuido a admin o api_key:<id>. GET /api/prompts/:id/versions?page=1 (20 por página) y POST restore {version,expected_version}. La UI captura versión al iniciar edición, no desde polling. Nueva versión incrementa configHash; se preservan las revalidaciones existentes.
- Migración 006 crea agent_documents: original BLOB, texto extraído, nombre, tipo, tamaño, revisión, estado y error. Convierte business_context existente en un documento TXT, conservando su contenido; las columnas legacy permanecen fuera del contrato editable. No se guardan Base64 ni archivos en disco.
- Límites: 5 MiB por archivo, 10 documentos y 30000 caracteres de texto disponible por agente. TXT/MD UTF-8, Word DOC/DOCX, PDF con capa de texto. Rechazar vacíos, formatos incompatibles, archivos cifrados y escaneados; no OCR. Extraer en worker thread limitado a 128 MiB V8/15 segundos, una extracción simultánea por instancia; bibliotecas word-extractor y pdfjs-dist. No ejecutar macros, HTML ni enlaces. Original conservado incluso si la extracción falla; descarga siempre autenticada como attachment.
- GET/POST /api/ai_agents/:id/documents, GET/PUT/DELETE /api/ai_agents/:id/documents/:documentId y GET .../:documentId/download. Subida binaria application/octet-stream con X-Filename codificado; sin multipart ni Base64. Lectura permitida por resources:read; mutaciones solo sesión/Origin. Sustitución/eliminación requieren If-Match de revisión. Reemplazo conserva el documento vigente hasta terminar y valida cuotas nuevamente en transacción; fallos no destruyen datos. Al arrancar, estados processing interrumpidos pasan a error visible.
- El runtime y las pruebas leen los documentos ready al iniciar cada ejecución. Inyectan su texto nombrado como referencia separada del system prompt; configHash incluye IDs/revisiones y el envío se revalida. No hay llamada de búsqueda ni lectura del binario por el modelo.
- Modelo único desde LLM_MODEL y proveedor desde LLM_BASE_URL/LLM_API_KEY. Quitar campos provider/model del contrato y UI de agentes; ignorar valores legacy al ejecutar. Validación solo del modelo configurado, sin overrides desde la petición.
- POST test {message,prompt?,history?,context_hash?}: historial alternado user/assistant de hasta 20 mensajes/18000 caracteres; no roles system/tool. Instrucciones candidatas hasta 20000, contexto actual y tools simuladas. Una prueba concurrente, 5/min, 3 rondas, 5 tools, 60s; devuelve documentos usados y usage nullable. context_hash de la respuesta anterior obligatorio al continuar; chat en memoria del navegador, reinicio explícito y sin colas ni datos operativos. Cambiar candidato o documentos/configuración obliga a iniciar una nueva conversación de prueba para no mezclar versiones.
- Agente con una sola fila de cuatro pestañas accesibles, Instrucciones/Herramientas/Contexto/Probar. Lista de cargas inmediata con estados y errores. Abrir muestra texto extraído y descarga original; reemplazo transaccional. Editar agente conserva nombre, descripción y estado; las asociaciones se editan en su propia sección, enviando únicamente los campos modificados. Probar ocupa su pestaña y conserva el chat al cambiar de sección; no hay pestaña Configuración ni panel lateral permanente de pruebas.
- Sitio público estático compilado desde Markdown versionado con una lista explícita de páginas, sin incluir docs privados. Comando build:docs genera dist/docs y copia al public/docs del frontend; build de app y Docker lo incorporan en /docs/. Enlaces relativos permiten hosting independiente/subruta. Guías de instalación/env, operación, documentos, pruebas, API, despliegue/respaldos, contribuciones/licencias. Navegación móvil, teclado, búsqueda y enlaces directos. Incluir copia en build de landing y enlaces de app/landing; CI construye docs. Sin backend ni login para docs.

## Risks / Trade-offs
- Pruebas consumen tokens → advertencia y límites; fixtures de tools no prueban efectos reales.
- Documentos pueden contener instrucciones maliciosas → datos separados y tools permitidas, sin prometer eliminar prompt injection.
- Historial crece → snapshots acotados por tamaño de prompt; borrado explícito del prompt elimina historial cuando no tiene vínculos. No almacenar conversación ni pruebas adicionales.
- Edición API incompatible con clientes antiguos → documentar expected_version; UI actualizada y pruebas de conflicto.

## Migration Plan
Migración aditiva al arrancar; verificar base preexistente y SQLite temporal. No arrancar base local operativa ni desplegar en esta sesión. Respaldar antes de futura publicación; no revertir SQL aplicado. Build/specs/tests y QA visual con datos sintéticos.
